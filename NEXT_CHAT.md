# Передача разработки следующему чату

## Цель и запреты на случайные переделки

Продолжать реализацию дашборда координаторов по `материалы/МТС.pdf`.
Сохранить визуальную основу предоставленного HTML и четырёх скриншотов:
два экрана, компактные карточки, графики, дневная и ночная темы, акцент МТС.
Не начинать проект с нуля и не менять стек без причины. Изменения вести этапами,
проверять, сохранять исходники и обновлять этот файл перед передачей.
Переписка из другого чата не является доказательством реализации: проверять код.

## Сначала восстановить рабочее окружение

1. Прочитать START_HERE.md, IMPLEMENTATION_STATUS.md, README.md, DATA_CONTRACT.md.
2. Распаковать ZIP целиком. Node.js 24+. Выполнить `npm ci`, `npm run build`,
   `npm test`, `npm run validate`, `npm run test:local`, `npm run test:auth`.
3. Запустить `npm run dev`, проверить четыре группы, поиск, карточку, видеостену,
   светлую/тёмную темы и `/guide.html`. Не открывать HTML через file://.
4. Исходный коммит/контрольные суммы находятся в TRANSFER_MANIFEST.json.
   ZIP переносит код и исходный массив, но не текущую рабочую базу D1, аккаунты, сеансы и секреты.

## Последнее принятое решение пользователя

Исполнителей оставить, а сервисы и суть сбоев сделать относящимися к МТС.
Все такие происшествия должны оставаться явно симулированными.
Это реализовано в v13: фронтенд проектирует исходный снимок через
`lib/mts-simulation.mjs`. Исходный массив/API/база и атрибуты групп не меняются.
Переключатель или `?dataset=source` показывает оригинал. Импорт сравнивает
`sourceData.originalSnapshot`, а не вымышленное представление.
Не удалять переключатель и не подменять оригинальный JSON демоданными молча.
Полный отдельный демонабор есть в `data/mts-simulation.json`.

Для ITSM добавлена учебная отдельная страница. Это демопереход, не реальный
доступ к МТС. Соответствие такой замены оценке жюри не подтверждено.
Пользователь хочет сосредоточиться на ТЗ хакатона. Корпоративный SSO и
промышленную интеграцию не превращать в обязательные условия завершения демо.
Собственный базовый вход без зависимости от внешнего аккаунта выполнен в v15.

## Не нарушать правила ТЗ

- priorityId: 1 низкий, 2 средний, 3 высокий, 4 критический.
- Критические/высокие группы включают только активные инциденты.
- Координаторы: точная строка `КЦ ИТ Координаторы Массовых Инцидентов`;
  исследование тоже может быть на координаторах и входить в две группы.
- Research/20: сервис уже восстановлен; не считать активной просрочкой.
- stateEnum имеет приоритет; коды 7/10 в словаре расходятся с выгрузкой.
- Заполненное solution не закрывает активный инцидент. Удаление записи не означает решение.
- null-дедлайн не выдумывать; sysId хранить строкой без потери цифр.
- Исходный формат массива не менять и чужие 142 записи из макета не подставлять.
- Исходный массив: 44, активных 24, завершённых 15, исследование 5;
  группы 0/2/1/5, уникальных в фокусе 8, продуктов 5, команд 22.
- Исторические даты массива не выдавать за события последнего часа.

## Ближайший этап: подключение реальных интеграций

### 1. Яндекс и достоверный контекст помощника

Получить API-ключ и ID каталога у команды. Их можно сохранить редактором
через `/ai-settings`, шифрование уже подготовлено. Альтернатива — серверные
`YANDEX_API_KEY` и `YANDEX_FOLDER_ID` (они имеют приоритет). Не просить ключ в
общедоступном чате и не помещать его в код/ZIP. `YANDEX_MODEL_URI` необязателен.
Текущий API подготовлен для Alice AI LLM; перед подключением проверить доступную
модель по официальной документации Яндекса и доступам каталога, не подменять молча.
Ответ считается настоящей генерацией только после успешного запроса с
`provider=yandex`; configured=true означает лишь наличие настроек.

В v14 получение фактов уже перенесено на сервер: `assistantInput` читает
`loadIncidentData`, применяет `projectMtsSimulation` для view=mts-demo и
передаёт snapshot.simulation=true. В обычном запросе snapshot из браузера
отклоняется. contextMode=client_demo допускается с явной пометкой и только
анализом по правилам, без вызова Яндекса. Это не нужно переделывать заново.
Ответ содержит `context`: mode/view/revision/version/total/stale.
Локальный HTTP-мост перечитывает файл и для POST вопроса, не только GET дашборда.

Ближайший незавершённый шаг: настоящий ключ/каталог и реальная проверка
provider=yandex. Инструкция AI_CONNECTION.md; кнопка «Проверить ответ» на `/ai-settings`.
CLI `npm run ai:check -- --live` проверяет только переменные окружения, не D1.
Без --live только проверяются настройки. Наличие ключа не равно успешному ответу.
После подключения проверить неизвестный ID, null-дедлайн, изменение назначения,
недоступность провайдера и актуальность ответа относительно версии данных.
Проверено в v14: 77 тестов, 14 HTTP-сценариев и UI сводки с серверной версией.

### 2. ITSM и поток реальных данных

Получить пример реальной HTTPS-ссылки на инцидент. Настроить
`ITSM_INCIDENT_URL_TEMPLATE` с `{id}` или `{sysId}`. Проверить открытие реального
инцидента в учётной записи МТС. Ссылка появится в полной карточке; основной
выбор строки оставлен для контекста справа. Адрес productUrl для этого не годится.
Если нужен живой файл — настроить `INCIDENTS_SOURCE_URL` на общий HTTPS JSON.
Решить, достаточно ли опроса 5 секунд или нужен webhook/планировщик и SSE.

### 3. Самостоятельная авторизация и права — базовая часть выполнена

Не переделывать: `lib/auth.mjs` и встроенный bcrypt-модуль уже работают
в Worker и переносном Node. Новые миграции 0001 и 0002 не редактировать
после применения. Для первого редактора — AUTHENTICATION.md.
Если команда хочет закрыть публичную регистрацию, есть AUTH_REGISTRATION_OPEN=0.
Не включать это без её решения. Для промышленной эксплуатации позже добавить
восстановление пароля, приглашения, аудит ролей, MFA/SSO и разделение команд.
Локальный мост не доверяет внешним `oai-authenticated-*`; DEV_EDITOR_PREVIEW
сохраняется только для явной локальной проверки, не для публичного запуска.

### 4. Финальная проверка ТЗ перед защитой

Два устройства, один общий источник, деморежим выключен. Проверить последовательно:
новый критический; решение; назначение координаторам; высокий→критический;
новый срок; исследование у координаторов с null; уход с координаторов;
ошибочный JSON; конфликт двух редакторов; сеть пропала/вернулась; перезагрузка.
Проверить видимое уведомление, исчезновение из нужной группы, журнал и единый
счётчик уникальных ID. Уведомление о решении не должно исчезать незаметно.
Локальная автоматизация этих серверных сценариев уже есть, пользовательская
проверка уведомлений и двух физических устройств ещё нужна.

### 5. Затем улучшать продукт

Подключить справочник владельцев продуктов для обоснованных рекомендаций,
подготовить смысловые причины/источники ИИ, управление сменой, наблюдаемость,
резервные копии и нагрузочную проверку. Не тратить этап на новые галереи дизайна,
3D-логин и декоративные вероятности до закрытия интеграций и обязательного ТЗ.
